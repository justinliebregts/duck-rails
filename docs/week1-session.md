For fast train testing, select **Two Ducks** and press Play. **Duck Rails > Two Ducks Quick Start** is enabled by default: both authenticated editors join the same test expedition (excluded from public compound matchmaking) and spawn aboard without the public platform countdown. Either editor can finish sign-in first; the other uses normal late-join loading. The main editor reads `RailsQuickStart` from the selected scenario's main-instance configuration, because its runtime tag list can be empty/stale. The additional editor retains the runtime `Player2` tag for account selection and quick start. A random internal rendezvous token is shared through local project-scoped EditorPrefs, so other developers do not share a hard-coded room. It persists while a client remains connected; stopping both clients closes the room. Disable the menu toggle before Play to exercise normal compound boarding. Default solo Play and built players retain normal matchmaking. Finishing a test expedition returns the crew to a compound normally; quick start only applies at initial login.

Login has its own station art and keeps the existing random LoginSpot selection. Normally it authenticates, connects to the US Photon region, joins a twelve-player public compound, then loads Compound as a single scene. Only Login and Compound are enabled in build settings. Neither Main nor Quackville loads.

In Compound: WASD/mouse to move/look, Space to jump, left mouse to grip, Tab to open controls. The compact status banner sits at the top center and omits control hints. The Duck debug panel is available with F8, with no persistent Duck button. Footsteps measure walking relative to the carriage, so standing aboard a moving train is silent. The yellow platform is the public boarding trigger. The first occupant starts twenty seconds; an empty trigger cancels; re-entry restarts twenty seconds. Eight admitted players depart; additional occupants wait for the next departure. The board shows countdown and admission state.

Walk to the private terminal on the left, press Tab, enter five digits, and choose Create or Join. Create never silently joins an occupied code. In private staging, the current Master Client can Start expedition. The Join action accepts any live room code, including public compounds and public expeditions. Every room displays its five-digit code in the top banner, preserving leading zeroes. Anyone can join an expedition code while running if capacity (including reconnect reservations) allows.

The test carriage contains a loose bat and a loaded backpack. Any ready crew member can use Tab controls to GO or STOP during a running expedition. Non-master requests are sent reliably to the current master, which validates the sender's readiness and run ID and commits shared train motion. The latest request waits through an in-flight room update. Simulating success or failure and returning the crew remain master-only controls. The inherited E-to-spawn-bats debug shortcut is disabled in Rails rooms. Private return preserves the room/code. Public crews of one to four try an existing compound, falling back to a fresh one; five to eight use a fresh compound. Leaving the last connected player closes a private room immediately.

## Source and state

### Public crew return implementation

After either success or failure, the source Master Client freezes the connected crew and commits one return token. `RailCrewReturn.cs` opens a temporary, hidden Realtime coordination room using each player's existing authenticated identity. This is a control room, not a gameplay room; it has no avatar, world or voice, and its internal name is not a user-facing code. Gameplay and control use distinct rooms in the same app/version/region. This adds one short-lived connection per returning player; include that overhead in traffic/CCU testing.

For one to four players, one coordinator makes a single filtered random-room attempt with the entire crew in Photon's `expectedUsers`; the search budget is twelve seconds. Followers stay in the expedition until the coordinator has joined and publishes the secured five-digit destination. Five to eight players skip that search. A failed search, expired search lease or lost coordinator commits one common fresh allocation. Compare-and-swap prevents a late search result from replacing that fallback. If an existing destination fails during handoff, the common fallback also moves already-arrived members while the coordination connection is active. Private returns do not use this path.

The coordination room retains the decision through master succession and reconnects while members remain connected. All members acknowledge arrival before closing their control connections. The handoff is bounded to ninety seconds; persistent connection/control failures show an actionable error and retain the explicit Leave control rather than silently sending each player to independent matchmaking. Full simultaneous disconnection cannot retain an empty coordination room. Validate these recovery paths with real clients before accepting the milestone.

Destination expected-user slots have individual thirty-second leases stored in room properties. Cleanup updates the expected-user list and lease metadata together with a server compare-and-swap, so an outbound platform transfer or a concurrently arriving crew cannot clear another crew's slots. Missing lease metadata is initialized by the destination master, including orphan reservations from a coordinator that disappeared before publication. This replaces the old room-wide reservation expiry tied to `rails.transferUntil`.

Photon's supported team-reservation behavior and distinct-room connections with one identity are documented in [UserIDs and Friends](https://doc.photonengine.com/realtime/current/lobby-and-matchmaking/userids-and-friends). No new authentication identity or backend is introduced.

- `PhotonSession.cs`: connection, filtered compound matchmaking, five-digit private operations, roster freeze, transfer destinations, phases, run IDs, reconnects and timeouts. Preserves issued Photon auth during normal room transfers. Distinct app-version suffix separates the new state protocol from inherited Duckz rooms.
- `RailSessionRules.cs`: capacities, 120-second player TTL, zero empty-room TTL, allowed phase transitions, stable eight-player admission, countdown and deterministic train motion.
- `RailWorld.cs`: Compound/expedition presentation in one scene shell, local loading gate, master validation of platform membership against avatar pose, seeded room-owned supplies, current cargo manifest, desktop terminal and temporary test controls.
- `RailTrain.cs`: actual moving carriage using existing `Helicopter.MoveCabin` passenger support. The existing Photon avatar cabin-relative interpolation also supports the carriage.
- `RailCargo.cs`: train-relative loose-item replication, carry, release/overboard velocity handling. Existing `PhotonGrabbable`, `BagObject`, ownership and room recovery remain responsible for item interactions and bag contents. Recovery checkpoints include the cargo frame.
- `RailSceneBuilder.cs`: repeatable authoring command, **Duck Rails > Build Week 1 Scenes**. Requires saved scenes and Edit Mode. Produces Compound, Login art, materials and RailBat/RailBag prefab variants; original item/player prefabs are reused.
- `RailSessionChecks.cs`: **Duck Rails > Run Session Checks** validates policy, timing, capacity, motion integration and built asset references.

Room properties retain phase/revision, run ID, countdown/roster, transfer destination/users, reservation leases, test block, fuel, train motion and current cargo IDs. Phase commits use compare-and-swap revisions. Crew destination creation uses a five-digit name, an internal unique allocation token, and Photon expected-user reservations; any selected member can create it if the previous coordinator disconnects. Transfer reservations expire after thirty seconds. Public-return join failures use the coordinated fallback described above; ordinary failed code joins still return to the originating compound if possible, otherwise another compatible compound. Photon cannot distinguish a nonexistent code from one in a different app-version partition; the UI explicitly asks users to check both.

Private creators start as Master Client. Desktop focus changes do not move authority between windows; disconnects still trigger Photon succession. A rejoining owner rebinds the existing avatar, and inactive avatars are never mistaken for the master's local player. Slot recovery uses the authenticated Photon user ID. Bags/equipment are not recreated from local disk saves in Rails rooms. Gameplay supplies are shared and reset for each new run.

Private replay cleanup (October 29): compound/staging readiness now waits until the Photon registry contains no old cargo, and `StartPrivateRun` independently rejects a restart while any remains. Each connected client network-destroys the cargo it controls; the master handles room-owned cargo. Cleanup, seed detection and manifests use registered Photon views, including inactive/stowed objects, rather than an active-only scene search. This prevents a fast replay from bypassing the half-second cleanup tick. It also avoids asking the master to destroy another connected player's owned item without authority.

## Five-digit room allocation

All gameplay rooms use five-digit numeric names in schema 4 / the `-duck-rails-session-v4` partition. Restart every client on this build; older rooms cannot mix with the crew-return protocol. The banner shows the current code in public and private rooms. The private station's Join action accepts any live room code. Public departures and newly allocated return compounds get new codes; returning into an existing compound uses its code. Private staging/run/return preserves its code. Empty rooms still close immediately.

Private Create remains hidden and rejects occupied codes. Automatic rooms use the `rails-auto-v2` lobby: normal matchmaking filters to compounds, while transfers and Two Ducks quick start use server-side `JoinRandomOrCreateRoom` matching their unique allocation token, kind, and schema. Automatic rooms must be lobby-visible for token matching, but expeditions are excluded from normal compound discovery. Direct numeric Join works across both lobbies. Long internal transfer/run identifiers are not displayed room codes.

Occupied automatic candidates retry with the next deterministic code, up to 100 attempts with a one-second delay. The allocation filter prevents entering an unrelated room to inspect it, and lets later crew members find the matching allocation regardless of which candidate succeeded. Capacity and ending-phase restrictions still apply.

## Shared fuel behavior

`rails.fuel` is fuel at the starting distance of `rails.motion`, not a periodically decremented counter. The master commits both together on GO/STOP; every client uses the same Photon clock and motion integration to derive current fuel through `PhotonSession.CurrentFuel`. Late entry and master succession reconstruct from those retained properties without resetting fuel or relying on missed events. New runs start at 100; the current tuning burns 0.025 per metre (0.1 per second at cruise), including braking distance, and nothing at rest. The Tab display shows tenths. At zero fuel, motion is capped at the affordable distance and stops; smooth exhaustion braking and refuelling are future work. Fuel continues to follow motion during ending/returning while the train is still moving.

Rejoin persistence requires another connected client to keep the room alive: the existing last-player-leaves policy still destroys the room. Verify with two clients: GO and compare fuel, STOP and confirm idle stability, leave/rejoin the same code while the other continues, then disconnect the master and compare again. New private runs should reset to 100. Check rapid GO/STOP during pending room commits and zero-fuel stopping on both clients.

## Quick Start grab-surface startup failure — October 29, 2026

Investigated Justin's intermittent **1 Quick Start** failure. The Unity Console contains mesh vertex and triangle access errors immediately before the zero-triangle exception: the flashlight mesh has Read/Write disabled, and ordinary mesh reads were rejected during ExitingEditMode. GrabSurfaceBaker assumes those reads are always permitted in the editor. MCP inspection in Duck Rails Edit Mode found 303 vertices and 236 triangles with isReadable=false; BakeAll then passed. The zero count is therefore a failed mesh read, not evidence of an empty authored flashlight. Why this occurs only intermittently in the solo scenario is not established. Follow-up fix: GrabSurfaceBaker now uses editor-only MeshUtility.AcquireReadOnlyMeshData, copies vertices and per-submesh indices (including base-vertex offsets), and disposes the snapshot/native buffers. Existing topology filtering, transforms, degenerate-triangle filtering and triangle limits remain intact. Import Read/Write settings are unchanged. Editor sources compile with Unity 6000.3.24f1 Roslyn and the generated response file (zero errors, two existing warnings). MCP verified Duck Rails in Edit Mode before the change, then lost discovery; no Unity process remained available. Updated BakeAll output comparison and repeated 1 Quick Start launches remain unverified. Before the edit, surface hashes were captured to ignored Temp/grab-surface-before.json for comparison.
