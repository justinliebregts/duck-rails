# Enemy train boarding

November 6, 2026. The user wants minions and spiders to board and ride the moving train, and authorized starting with the minion. This replaces the earlier blanket no-boarding scope. The subsequent November 6 request also authorizes spider boarding through the rear and both side gaps.

## Implementation

`RailTrainNavigation` loads a separate editor-baked graph from `Assets/DuckRails/Train/TrainCrawlGraph.bytes`. Its cell keys and node data stay local to the train; world queries transform through the current carriage pose. Resumable A* computes distances in graph coordinates so movement between search slices cannot invalidate its heuristic. No runtime geometry bake or block-graph reconstruction is performed.

`RailZombie` and `RailSpider` opt into `RailEnemyBoarding`. They retain the existing brain, ground/climbing movers, gait, hit reactions and budgeted manager path service. Each enemy selects its navigation graph through a temporary manager scope; other enemies and companions continue using the world graph. Pathfinder instances are reused per graph.

Initial tuning: chase a passenger to a reachable ground graph node near the open rear or either side railing gap, walk a collision-checked and continuously supported approach, then climb onto the deck. Boarding is permitted at up to 0.6 m/s, with an approach within 8 m of an existing connected graph and a rise no greater than 1.8 m. Physical clearance is checked during the transfer. A fast departure, obstruction or excessive gap aborts the climb. These are implementation defaults, not confirmed final balance.

Once attached, the train carries the enemy and its cached movement/contact positions before ordinary AI movement. Losing physical train support detaches it into the existing fall/hit system. A dropped enemy can recover toward nearby world navigation and adopt the block where it actually lands. An aboard enemy cannot use the old home-spawn recovery to teleport back to its original block.

The 22-byte enemy packet carries a train-frame flag, an outside-block flag, local position/rotation and train-local aim for ordinary enemies when aboard. Spiders send head-local aim and a separate requested-lift byte. A heartbeat bit refreshes stationary minion snapshots twice per second even with PUN's UnreliableOnChange transport. Melee confirmations include their coordinate frame. The current build compatibility suffix is **_dra2** (raised-spider port, November 8); this supersedes the historical session-v12 label. Use updated clients together.

Train passengers enter the shared target list. Opted-in minions and spiders can perceive them, and spider passive stalking can approach them; other enemies still exclude passengers. A passenger down request must identify a nearby, active boarded enemy; generic down requests and bomber blasts retain their passenger protection. Ending-phase damage is rejected.

## Fast iteration

Temporary spider-only playtest: RailEnemySpawns.ForcedEnemyType = 3 overrides newly spawned expedition enemies to RailSpider, preserving spawn counts, positions and seeded encounter choices. Set it to -1 to restore the normal mix (0 selects minions). Start a fresh expedition to replace enemies already spawned in a room. This applies to builds as well as the editor.

- **Duck Rails > Authoring > Bake Train Enemy Navigation** rebuilds only the train navigation asset and installs its prefab component plus minion/spider opt-in. Save open scene edits first.
- **Duck Rails > Tests > Enemy Boarding > Graph And Network Checks** checks the bake, transformed node lookups, deck pathfinding and packet flags.
- **Run Isolated Play Loop** uses the actual depot, train and minion in a temporary offline Play Mode scene. An inactive login sentinel avoids automatic authentication; scene setup is restored afterward. This tests natural boarding, exact carried pose, ordinary deck pursuit and the real melee shove/fall code.
- **Navigation Regression** runs the existing resumable search, ground/climb replacement and shared scheduler cases without closing the editor.
- **Run Two Client Network Loop** launches the existing two-client MPPM scenario using saved distinct accounts. It uses explicit fixture placement for transport tests and the actual Photon pose/RPC/room paths. **Stop Network Loop** disarms it and stops the scenario; the prior scenario and quick-start setting are restored.

Evidence goes in `docs/validation/enemy-boarding/`. None of these tools queries or resolves diagnostic reports.

## Spider boarding — November 6 follow-up

Spider uses the same authored rear/left/right transfer points and collision/landing checks. The transfer component now works with either the ground mover or the climbing mover, using the spider's actual sphere radius for clearance. Climb path goals route through the selected opening, direct pursuit cannot bypass a transfer, and world-graph movement avoids train occupancy. Both combat pursuit and passive stalking can board. Existing minion boarding remains enabled.

The climbing mover carries contact normals, steering and recovery caches with the train. Spider gait also carries body/velocity history and planted/swinging feet, avoiding false walking motion caused solely by train translation. Aboard support is checked along the spider's contact normal against an actual train collider, including walls. Authority handoff initializes that normal from the replicated root before checking support. The existing world-anchored web is cancelled while aboard or transferring; no moving-train web mechanic is introduced. The train's existing bake still excludes ceilings.
